# 语音时间管理产品：MVP 产品文档与 P0/P1/P2 路线图

> 文档状态：讨论基线
>
> 本文用于替代原 TimeFlow Wiki 中过大的 MVP 范围。当前版本只聚焦个人时间管理，不包含共享、团队协作、Goal 管理或自动排期。

## 0. 项目规范对齐

本文遵循项目官方 Wiki 的工作要求：先产品、再架构、后开发；每轮只交付一个可验证的增量；所有取舍必须写明理由、边界和验收方式。

本 Proposal 直接回答五个问题：

1. 用户是谁：需要快速管理个人安排和日常事项的个人用户。
2. 问题是什么：输入成本高、事项容易遗漏、提醒缺少执行闭环。
3. 为什么值得做：验证语音是否能降低时间管理操作成本，以及情境提醒是否能提高事项完成率。
4. 怎么做：语音驱动日历、待办和提醒；先做一次性事项、单次时间提醒和基础地点提醒，再按数据扩展。
5. 怎么验收：本周先跑通一条真实闭环，后续以标准用户故事、成功率和误执行率持续验证。

本文件的 P0/P1/P2 是产品优先级，不替代官方 Milestone、Issue、PR 和 Review 流程。文档定稿后，范围变更应新增决策记录，不覆盖原判断。

## 1. 产品定义

### 1.1 产品定位

这是一个以语音为主要操作方式的个人时间管理工具。用户可以用自然语言管理日历事项和待办，并在合适的时间或地点收到提醒。

一句话描述：

> 用户说一句话，系统把事情记下来，并在该做的时候提醒用户。

### 1.2 核心用户问题

- 打开日历或待办应用、定位日期和填写字段的成本太高。
- 临时想到的事情容易忘记，尤其是在不方便打字时。
- 单纯按时间提醒无法覆盖“到家后”“回到停车场后”这类情境。
- 提醒触发后缺少完成、延后和取消的闭环。
- WS 只能保证活跃会话的实时同步，不能假设 App 后台或被系统杀死后仍持续在线；断线后必须能补拉状态。
- 本期只做单设备，不做多设备抢写、抢提醒或跨设备主从切换；本地改动先入本地缓存，再上传到服务端，最后以服务端回传的最新状态覆盖本地视图。

### 1.3 目标用户

本期面向需要管理个人安排和日常事项、且经常通过手机语音输入的用户。重点场景包括通勤、驾驶前后、家务、个人事务和临时安排。

不以团队、家庭协作、项目管理或长期目标管理用户为本期目标。

## 2. 核心概念

### 2.1 日历事项 CalendarEvent

表示在某个时间段发生的安排，例如会议、预约、课程和健身。

MVP 必须有开始时间；结束时间可以通过用户输入或明确的默认规则补齐。无法安全补齐时必须反问。

### 2.2 待办 Todo

表示需要完成的事情，例如买牛奶、提交材料和取快递。

待办可以没有具体开始时间，但可以有截止时间和提醒时间。

### 2.3 提醒 Reminder

提醒是日历事项或待办的触发规则，不是第三种独立的任务对象。

MVP 支持时间触发和基础地点触发。一个事项是否能设置提醒、提醒何时触发和提醒状态，都由提醒规则表达。

提醒可以继续分成两层：优先级决定提醒力度，通道决定怎么触达用户。当前 MVP 激活本地提醒通道；架构保留云端兜底通道，当本地路径不可达或未确认送达时，可按优先级升级到短信、邮件或电话。

### 2.4 位置情境提醒

位置提醒是 P0 提醒能力的一部分，不是停车模块、地点管理产品线或通用记忆模块。

- “到家后取快递”：位置提醒绑定 Todo。
- “回到停车场提醒我车在哪里”：位置提醒可以不绑定 Todo，但内容仍然是一个需要稍后处理的个人事项。

## 3. 最小 MVP 定义

### 3.1 MVP 必须验证的假设

1. 语音输入能明显降低创建和修改个人事项的步骤。
2. 用户愿意通过语音查询当天或近期安排。
3. 确认后写入可以减少误创建、误修改和误删除。
4. 时间和地点两类基础提醒足以让用户形成“记录后被提醒”的使用闭环。

### 3.2 MVP 功能范围

#### 语音输入

- 录制短语音并完成 ASR 转写。
- 将转写内容解析为一个目标操作。
- 支持必要反问，例如补充时间、地点、事项对象或提醒时间。
- 支持基础指代消解，例如“刚才那个”“这个提醒”“明天的会议”。
- 识别结果在执行前展示给用户。

#### 日历事项

- 新增一次性日历事项。
- 查询今天、明天、本周和指定时间范围的事项。
- 修改标题、开始时间、结束时间、地点文本和备注。
- 删除事项。
- 为事项设置一个时间提醒或基础地点提醒。

#### 待办

- 新增待办。
- 查询未完成、已完成和指定时间范围的待办。
- 修改标题、截止时间、备注和提醒时间。
- 标记完成、取消完成和删除。
- 为待办设置一个时间提醒或基础地点提醒。

#### 提醒

- 一个事项可以有多个提醒，每个提醒都是一条独立规则。
- 支持指定时间提醒，或根据事项开始/截止时间计算一个提醒时间。
- 支持基础地点提醒，包括到达固定地点、离开固定地点和回到当前记录地点。
- 使用本地通知触达，至少覆盖通知、震动或语音播报中的一种。
- 提醒可以被确认、取消或简单延后一次。
- 事项修改、删除或取消后，旧提醒必须失效。
- 所有提醒必须绑定事项；停车位置、回到这里等独立地点提醒由系统创建轻量 Todo 后再绑定提醒。

#### 提醒状态

P0 提醒至少支持以下状态：

| 状态 | 说明 |
| --- | --- |
| `pending` | 已创建，等待时间或地点条件 |
| `armed` | 已布防，主要用于回到地点提醒，表示已离开原地点，等待再次进入 |
| `triggered` | 触发条件已满足 |
| `delivered` | 已交给本地通知或前台提醒展示 |
| `dismissed` | 用户确认或关闭提醒 |
| `snoozed` | 用户延后一次 |
| `cancelled` | 事项删除、提醒取消或规则失效 |
| `expired` | 一次性提醒超过有效期未触发 |
| `failed` | 权限、定位或通知投递失败 |

#### 智能提醒分层

智能提醒不是一个独立入口，而是提醒能力的增强：

- 本地智能提醒：基于时间、地点、通知权限和用户时区，在设备本地触发和展示提醒。P0 激活时间和基础地点提醒。
- 云端提醒：基于短信、邮件、网络电话等云端通道进行兜底或升级触达。当设备 WS 离线、本地服务被系统杀死、本地通知注册失败、提醒触发后没有设备回执，或用户配置了高优先级兜底时，系统可以按策略切到云端提醒。
- 远程推送提醒：若后续使用 Expo Push Service，Android 远程推送底层会依赖 FCM；没有 Google Play services 的 Android 设备链路不可靠，MIUI 等系统的省电和后台限制也可能造成延迟或拦截。
- 环境智能提醒：天气、噪声、设备状态、空气质量、交通等条件。P0 不激活，后续根据真实需求增加。

#### 提醒分级策略

| 优先级 | 目标机制 | 当前阶段 |
| --- | --- | --- |
| 普通 | 本地通知 | MVP |
| 重要 | 本地通知 + 震动 + 语音播报 | P1 |
| 紧急 | 短信、邮件、网络电话等云端通道，配合本地兜底 | P2 |

优先级只用来决定提醒机制，不引入新的产品线。P0 阶段只落本地通知，优先级先体现在提醒强度和展示方式上，不接云端通道。

#### 本地与云端兜底策略

提醒投递优先使用本地路径：

```text
本地通知 / 前台 WS
  -> 设备注册成功
  -> 到时间或地点条件满足
  -> 设备展示提醒
  -> 回传 delivered / failed / dismissed
```

当本地路径不可用时，后续可升级到云端路径：

```text
设备 WS 离线
或本地通知注册失败
或本地服务被系统杀死且无回执
或高优先级提醒超过等待窗口
  -> 云端按策略发送短信 / 邮件 / 网络电话
```

边界：

- 时间提醒可以由云端按服务端时间兜底触发。
- 地点提醒依赖设备侧定位事件；如果设备进程被杀且没有位置事件回传，云端无法凭空知道用户是否到达或离开地点，只能在用户配置的兜底时间窗口后发送“可能错过的地点提醒”。
- 云端短信、邮件和电话属于后续激活通道；P0 先保留策略和状态，不接真实供应商。

#### 基础界面

- 单页主面板。
- 主体是日程视图，支持今日、周、月切换。
- 日程视图展示手动添加事项和语音创建事项。
- 待办和提醒不作为独立一级页面，绑定在日程或待办事项中展示。
- 底部固定语音输入按钮。
- 语音弹出层采用卡片式交互，展示转写、反问、候选、确认和结果。
- 提醒通知后的完成、取消和延后操作通过通知动作或卡片浮层处理。

语音是主要操作入口；界面只作为一个日程主面板展示和处理结果，不再拆多页导航，也不承载另一套独立业务逻辑。语音交互使用底部弹层卡片完成，不跳转页面栈。

#### 日程视图展示规则

- 页面主体统一使用事项卡片展示。
- 主对象只有 `CalendarEvent` 和 `Todo`。
- 提醒只作为事项上的 badge 或副文案展示，不单独作为一级列表。
- 单个事项可以挂多个提醒，默认折叠展示，超过两个时显示 `+N`。
- 点击事项卡片后，在底部卡片中展开详情、编辑和提醒操作。
- 完成、取消、删除都通过卡片内动作完成，不跳转页面。
- 时间视图以时间优先，地点提醒以 badge 和副文案补充展示。

#### 语音弹层顺序

语音弹层按固定顺序展示卡片，状态变化时只切换当前卡片，不跳页面：

1. 录音卡
2. 转写卡
3. 反问卡
4. 候选卡
5. 确认卡
6. 结果卡

规则：

- 有录音时先显示录音卡。
- 转写完成后自动切到转写卡。
- 缺参时显示反问卡。
- 多候选时显示候选卡。
- 需要写入时显示确认卡。
- 写入完成、失败或取消后显示结果卡。

#### ItemCard 字段优先级

##### 日历事项

展示顺序：

1. 时间
2. 标题
3. 地点
4. 提醒 badge
5. 备注摘要

动作顺序：

1. 编辑
2. 提醒相关动作
3. 删除

##### 待办

展示顺序：

1. 标题
2. 截止时间或提醒时间
3. 提醒 badge
4. 状态
5. 备注摘要

动作顺序：

1. 完成 / 取消完成
2. 编辑
3. 删除

##### 提醒 badge

- 提醒 badge 按时间优先、地点其次排序。
- 多提醒默认折叠展示，超过两个显示 `+N`。
- 提醒动作只挂在提醒 badge 或底部详情里，不直接占用主动作位置。
- 提醒相关动作顺序：延后、取消提醒、编辑规则。

##### 重复 badge

- 重复 badge 只在重复规则存在时显示。
- 重复 badge 排在提醒 badge 之前。
- 重复 badge 只显示简短摘要，不展开完整规则。
- 文案示例：
  - `每天 8:00`
  - `工作日 8:00`
  - `周一·周三·周五 8:00`
  - `每天到家后`
  - `工作日到公司 8:00`
- 如果同一事项同时有重复规则和提醒规则，先显示重复 badge，再显示提醒 badge。
- 重复 badge 只表达系列规则，不表达单次 occurrence。

示例：

```text
15:00 - 16:00  项目会
地点：会议室 A
提醒：提前 15 分钟 · 到公司后
```

```text
取快递
状态：未完成
提醒：到家后 · 回到停车位置 +1
```

### 3.3 MVP 典型用户场景

| 场景 | 用户表达 | 预期结果 |
| --- | --- | --- |
| 新增日历 | “明天下午三点开项目会” | 解析后确认并创建日历事项 |
| 新增待办 | “记得买牛奶” | 创建未完成待办 |
| 查询安排 | “我今天有什么安排？” | 返回当天日历和待办 |
| 修改事项 | “把明天的会议改到四点” | 定位唯一事项，确认后修改 |
| 删除事项 | “取消明天的会议” | 定位事项，强确认后删除 |
| 完成待办 | “牛奶买好了” | 将对应待办标记完成 |
| 设置时间提醒 | “提前十五分钟提醒我开会” | 为会议创建一个时间提醒 |
| 设置地点提醒 | “到家后提醒我取快递” | 确认地点后创建一个到达地点提醒 |
| 处理提醒 | “十分钟后再提醒” | 延后当前提醒一次 |

### 3.4 MVP 确认和反问规则

- 查询不需要确认。
- 新增、修改和删除必须在落库前确认。
- 删除属于高风险操作，必须明确说明对象。
- 多个事项匹配时必须让用户选择，不能猜测。
- 缺少关键时间时必须反问，不能随意补全。
- 缺少关键地点时必须反问或让用户选择已保存地点，不能用模型猜测坐标。
- 一次只追问一个最影响执行的问题。
- 用户说“确认”“取消”“改一下”等回答时，应关联最近一个待处理操作。
- 指代消解只能使用当前会话、最近待确认操作、明确时间范围内的候选事项；无法唯一定位时必须反问。

### 3.5 MVP 不做

- Goal、Task、子任务树、项目管理和长期目标拆解。
- 自动排期、自动重排或静默移动已有日程。
- Feedback、周期复盘和用户画像。
- 共享日历、家庭待办、团队协作和权限协同。
- 图片、OCR、邮件、IM 和第三方日历聚合。
- 持续监听、后台录音和持续位置轨迹。
- 短信、邮件、网络电话等云端提醒通道。
- 天气、噪声、空气质量、交通和复杂设备状态条件。
- 多会话、复杂记忆库和任意知识记录。
- 多次提醒、重复规则、复杂免打扰和多渠道通知。

## 4. P0/P1/P2 功能路线

优先级只表示产品路线，不代表所有功能同时开发。每个阶段都必须以前一阶段的数据和用户反馈为进入条件。

### 4.1 P0：最小 MVP

#### P0 必做

- 语音 ASR 和命令解析。
- 日历事项的一次性 CRUD 和查询。
- 待办的一次性 CRUD、查询和完成。
- 单事项多提醒，支持时间触发和基础地点触发。
- 写入确认和对象歧义反问。
- 今日视图、待办列表和确认卡片。
- 本地通知。
- 基础失败提示和人工重试。
- 基础地点提醒：设置固定地点，支持到达/离开触发；允许一键保存当前地点，支持再次回到该地点时触发。
- 固定地点类型：先支持“家”“公司”和自定义地点。
- 临时地点类型：P0 先聚焦停车位置，保存当前坐标、定位精度、用户文字描述、触发半径和创建时间。
- 停车位置不是室内停车系统；P0 不识别楼层、区域、柱号或车牌，只保存用户说出的文字描述。
- 地点提醒半径允许用户选择，默认 `100m`，可选 `50m / 100m / 200m`。

P0 地点提醒只支持一次性规则，不支持复杂地点管理、停留条件、时间地点组合、天气条件或持续轨迹分析。

### 4.2 P1：提醒和事项能力增强

#### 日历增强

- 重复日历事项。
- 日、周视图和语音日程摘要。
- 简单冲突提示。
- 事项模板，例如会议、课程和预约。
- 用户主动把待办安排到指定时间段。

#### 待办增强

- 优先级和标签。
- 截止时间与逾期状态。
- 重复待办。
- 批量完成、批量延后和批量删除。
- 日历事项与待办之间的明确转换。

#### 提醒增强

- 多提醒管理增强，例如查看、编辑和批量删除提醒。
- 重复提醒。
- 延后、稍后提醒和逾期提醒。
- 提醒确认记录。
- 修改事项后重新计算提醒。
- 基础免打扰时段。
- 低/中/高优先级映射到不同提醒通道。
- 云端提醒作为高优先级扩展入口，包括短信、邮件和网络电话。

#### 最小重复规则

重复规则只保留最小集合，用于习惯型提醒和固定节奏事项：

- `daily`：每天重复
- `weekdays`：工作日重复
- `custom_weekdays`：自定义周几重复，例如周一、周三、周五

约束：

- 必须至少指定一个 `time_of_day`，地点重复还要指定 `place_id`
- 允许时间 + 地点组合，例如“工作日到公司提醒我打卡”
- 允许地点触发的重复规则，例如“每天到家后提醒我运动”
- 不支持月度规则、年度规则、cron 表达式、复杂例外、单次补做、单次跳过、单次例外编辑
- 重复规则只支持整条系列的开启、关闭和未来修改，不支持单次 occurrence 独立改写
- 重复规则可用于日历事项、待办提醒和基础地点提醒
- 重复规则与普通提醒各自独立触发，但展示时仍归在同一事项卡片内
- 复杂例外统一不做；删除和停用只支持整条系列级别操作，不支持单次 occurrence 独立删除或改写

#### 重复规则确认卡片

重复规则的确认卡片固定显示以下字段：

1. 规则标题
2. 重复类型：每天 / 工作日 / 自定义周几
3. 重复时间：`time_of_day`
4. 重复日期：起始日期和可选截止日期
5. 地点：仅地点型重复时显示
6. 触发方式：时间 / 地点 / 时间 + 地点
7. 生效范围：仅未来系列
8. 提醒方式：本地通知，后续可扩云端兜底
9. 风险提示：不支持单次例外和单次补做
10. 操作范围：仅整条系列

按钮顺序：

- 确认
- 编辑
- 取消

#### 云端兜底窗口

- 时间提醒：本地触发后等待 `60s` 未确认送达时进入云端兜底；高优先级可缩短到 `15s`
- 地点提醒：本地触发后等待 `5min` 未确认送达时进入云端兜底；高优先级可缩短到 `2min`
- 地点提醒云端兜底只做补救提示，不承诺替代设备侧定位事件

#### 语音交互增强

- “刚才那个”“下一个会议”等短指代。
- 连续语音确认。
- 一次请求中的有限批量操作。
- 对识别文本、解析结果和最终写入结果进行可追溯展示。

### 4.3 P2：位置增强和情境提醒

#### 位置增强能力

- 更多固定地点：家、公司、学校等。
- 更多临时地点：停车场、快递柜和临时会场。
- 更复杂的到达、离开和重新进入触发。
- 位置触发器的启用、停用和删除。
- 更完整的定位授权管理。
- 定位不可用时降级为文字位置记录或普通时间提醒。

#### 位置增强代表场景

- 到家后取快递。
- 离开家时提醒带文件或钥匙。
- 到公司后提醒提交材料。
- 回到停车场时提醒车位所在楼层、区域和用户描述。
- 到超市时展示购物待办。

#### 时间和位置组合

- 工作日到家后提醒。
- 在某个地点停留一段时间后提醒：用户进入地点后不立即提醒，只有持续停留超过指定时长才触发，例如“到公司 10 分钟后提醒我打卡”。
- 只有在指定时间窗口内到达地点才触发。

这些能力仍然属于 Reminder，不新增停车、家庭或地点管理产品线。

### 4.4 P2 后续候选：更智能的个人时间管理

以下功能只有在 P0/P1/P2 的核心使用数据证明需求后再评估：

- 用户主动请求的时间块安排。
- 日历冲突的多个调整建议，但不自动应用。
- 会议准备时间和出发时间提醒。
- 日/周执行摘要和提醒效果统计。
- 基于明确历史行为的提醒建议，但写入仍需确认。
- 锁屏、耳机、手表和车载模式等免手入口。

不在当前路线中恢复 Goal、自动排期、复杂重排、团队协作或共享功能。

## 5. 关键交互流程

### 5.1 新增流程

```text
用户说话
  -> ASR 转写
  -> 识别 entity 和 action
  -> 补齐必要参数
  -> 展示候选
  -> 用户确认
  -> 写入日历或待办
  -> 创建提醒
```

### 5.2 查询流程

```text
用户说“我今天有什么安排”
  -> 解析时间范围
  -> 查询日历和待办
  -> 返回简短列表
  -> 支持继续追问或语音操作
```

### 5.3 修改和删除流程

```text
用户表达修改或删除
  -> 按时间、标题和状态查找候选
  -> 唯一则生成变更预览
  -> 多个则让用户选择
  -> 用户确认
  -> 原子更新事项和提醒
```

### 5.4 位置提醒流程（P0 基础 / P2 增强）

```text
用户说“到家后提醒我取快递”
  -> 确认家地点和定位权限
  -> 创建 Todo
  -> 注册一次性位置提醒
  -> 进入家地点后通知
```

归类：

- 产品能力：P0 基础地点提醒。
- 业务对象：`Todo(title=取快递)` + `Reminder(trigger_type=enter_place, place=家)`。
- 提醒通道：P0 使用本地通知。
- 写入方式：作为一个复合 `WriteRequest` 展示给用户确认后再写入。
- 边界：如果用户当前已经在“家”范围内，系统不能立即触发，应反问“要下次到家时提醒吗？”或将规则设置为离开后再次进入才触发。

```text
用户说“我车停在这里，B2 区 17 号柱旁”
  -> 保存当前坐标、精度和文字描述
  -> 等待用户离开停车区域
  -> 再次进入停车区域后提醒
  -> 保留记录供“我的车停在哪里”查询
```

### 5.5 P0 提醒触发故事

#### 时间提醒

```text
用户说“明天上午九点提醒我交材料”
  -> 解析提醒时间
  -> 创建 Todo：交材料
  -> 创建 time reminder
  -> 用户确认
  -> 到时间后本地通知
```

规则：

- 时间提醒必须保存为绝对时间，展示时使用用户时区。
- 用户说过去时间时必须反问，不能创建已经过期的提醒。
- 用户只说“明早”“晚上”等模糊时间时，应根据默认规则生成预览；无法安全补齐时反问。

#### 到达地点提醒

```text
用户说“到家后提醒我拿快递”
  -> 解析 Todo：拿快递
  -> 定位 Place：家
  -> 创建 enter_place reminder
  -> 用户确认
  -> 下次进入家附近后本地通知
```

规则：

- 到达地点提醒必须有已确认地点和触发半径。
- 如果用户当前已经在地点范围内，不能立即触发。
- 当前已在地点内时，系统必须反问：“你现在可能已经在家，要下次到家时提醒吗？”
- 用户确认后，规则应等待用户离开该地点后再次进入再触发。

#### 离开地点提醒

```text
用户说“离开家提醒我带钥匙”
  -> 解析 Todo：带钥匙
  -> 定位 Place：家
  -> 创建 leave_place reminder
  -> 用户确认
  -> 离开家附近后本地通知
```

规则：

- 离开地点提醒必须有已确认地点和触发半径。
- 如果用户当前不在该地点，系统应提示“你当前可能不在这里，仍要创建吗？”
- 用户确认后可以创建，但预览里必须展示该风险。

#### 回到当前地点提醒

```text
用户说“我车停在这里，B2 区 17 号柱旁”
  -> 一键保存当前地点
  -> 创建轻量 Todo：回到停车位置
  -> 创建 return_to_place reminder
  -> 用户确认
  -> 等待用户离开半径
  -> 离开后进入 armed
  -> 再次进入半径后本地通知
```

规则：

- 回到当前地点提醒只用于当前位置保存类场景。
- 创建时不能立即触发。
- 必须先检测到用户离开半径，提醒进入 `armed` 状态后，下一次进入才触发。
- 只触发一次。
- 系统保存用户文字描述，不结构化识别楼层、区域、柱号、车牌或室内位置。

#### 地点半径和定位精度

```text
默认半径：100m
可选半径：50m / 100m / 200m
```

规则：

- 确认卡片允许用户调整半径。
- 如果定位精度差于触发半径，例如精度 300m、半径 100m，系统允许创建，但必须提示“定位不精确，提醒可能不准”。
- 用户拒绝定位权限时，系统不能创建后台位置监听。
- 定位权限拒绝后的默认降级是普通 Todo + 文字地点记录，也可以让用户改成时间提醒。

## 6. 功能边界和产品原则

- 语音是主要入口，但用户始终能在界面看到和确认结果。
- 事实写入必须可见、可确认、可撤销。
- 系统不应静默改变用户已有安排。
- 时间无法确定时追问，不能用模型猜测代替事实。
- 指代无法唯一消解时追问，不能用模型猜测代替用户选择。
- 位置能力必须显式授权，不做持续轨迹记录。
- 位置不准确时优先展示用户的文字描述。
- 提醒只推动用户行动，不自动标记完成。
- 同一事项的提醒、完成和删除要保持一致。
- 任何新增能力都必须服务于日历、待办或提醒三者之一。

## 7. MVP 验收标准

### 7.1 功能验收

- 用户可以用语音创建一次性日历事项。
- 用户可以用语音创建待办并标记完成。
- 用户可以查询今天、明天、本周的日历和待办。
- 用户可以修改和删除唯一匹配的事项。
- 多候选时系统要求用户选择。
- 新增、修改、删除未确认前不改变正式数据。
- 用户可以为事项创建一个时间提醒。
- 用户可以为事项创建一个基础地点提醒。
- 用户可以为同一事项创建多条提醒，且多条提醒互不覆盖。
- 提醒触发后，用户可以确认、取消或延后一次。
- 删除或修改事项后，旧提醒不会继续触发。
- 用户可以通过反问补齐缺失时间、地点和事项对象。
- 用户可以用“刚才那个”“这个提醒”等短指代继续处理最近待确认操作。
- 单页主面板可以展示今日、周、月日程视图；待办和提醒以事项附属信息出现。
- WS 断线后再次进入应用，主面板状态能补拉恢复。
- 单设备下，本地编辑后会先显示本地结果，再上传再下拉，最终以服务端最新状态为准。

### 7.2 质量验收

- 标准语音 CRUD 场景成功率不低于 80%。
- 高风险写入的未确认误执行率为 0。
- 多候选对象不得静默选错。
- 本地提醒在测试设备上的触达正确率不低于 95%。
- P0 基础地点提醒在真机测试中的触发逻辑可验证，不因创建时当前位置立即误触发。
- ASR 或模型不可用时，系统明确提示失败，不产生半成品数据。
- 时间解析使用用户时区，不能因服务端时区导致错时。

### 7.3 P0 基础位置提醒验收

- 到家取快递不会在创建时立即触发。
- 停车位置提醒必须在离开后再次进入才触发。
- 用户拒绝定位权限时，系统不会创建后台位置监听。
- GPS 不准确时仍能展示楼层、区域和车位文字描述。

## 8. 成功指标和进入下一阶段的条件

### P0 -> P1

- 语音输入到有效候选的完成率达到 60% 以上。
- 标准 CRUD 成功率达到 80% 以上。
- 高风险误执行率为 0。
- 用户能在一次使用中完成创建、查询和修改三类操作。
- 至少有一半试用用户愿意继续使用基础提醒。
- 至少一条基础地点提醒场景可以在真机上完整演示。

### P1 -> P2

- 基础提醒的查看或处理率达到 50% 以上。
- 延后、完成和取消等提醒操作被真实使用。
- 重复事项和多次提醒没有造成明显的误触达。
- 用户明确提出更多地点条件、环境条件或云端兜底需求，或基础位置场景测试中有稳定价值。

### P2 后续评估

- 位置提醒触发准确率达到 90% 以上。
- 定位权限接受率和提醒处理率达到可接受水平。
- 用户能理解位置提醒和时间提醒的差异。
- 电量、隐私和地下停车场精度问题有可接受的处理方案。

## 9. 风险与收缩路径

| 风险 | 处理方式 |
| --- | --- |
| ASR 错误导致事项错误 | 展示转写和结构化预览，写入前确认 |
| 时间表达不明确 | 只追问缺失字段，不默认猜测 |
| 事项定位不唯一 | 展示候选供用户选择 |
| 提醒过多造成打扰 | P0 支持多提醒，但每条提醒必须显式确认；后续再增加批量管理和复杂免打扰策略 |
| 位置精度不足 | 保存用户文字描述，位置只作为辅助 |
| 云端提醒接入成本高 | 先用统一提醒策略抽象通道；本地路径不可达时允许按优先级兜底到云端，真实短信、邮件和电话供应商后续接入 |
| Android 远程推送不可靠 | Expo/FCM 链路依赖设备推送环境；无 Google Play services 或 MIUI 后台限制时，应降级为本地提醒、前台 WS 同步或提示用户调整系统设置 |
| 地点提醒云端兜底不精确 | 地点触发依赖设备侧定位事件；设备被杀且无位置回执时，云端只能做延迟兜底提示，不能承诺准确到达/离开判断 |
| 用户不使用语音 | 保留基础界面操作作为故障和可访问性兜底，但不扩张独立产品流程 |
| 位置提醒不稳定 | P0 收缩为一次性基础地点提醒，优先保存文字描述和明确降级 |
| 需求再次膨胀 | 新需求必须归入日历、待办、提醒之一，并注明对应阶段和验收指标 |

## 10. 明确不进入本路线的功能

- 共享日历和家庭待办。
- 团队协作和多人排期。
- Goal、Task、子任务层级和项目依赖。
- AI 自动规划完整人生或工作计划。
- 静默重排已有日程。
- 通用知识库、长期个人记忆和任意笔记。
- 邮件、IM、第三方日历聚合。
- 后台持续录音或持续位置轨迹。

## 11. 当前产品决策

当前建议冻结为：

1. P0-MVP 交付语音日历、语音待办、基础时间提醒和基础地点提醒。
2. P0 激活本地提醒；云端提醒作为高优先级兜底能力保留策略和状态，真实短信、邮件和电话供应商后续接入。
3. P1 主要增强提醒和事项本身，不引入 Goal、项目和协作。
4. P2 主要扩展天气、噪声、设备状态、云端触达和更复杂的位置条件，不拆出停车或家庭产品线。
5. 后续所有功能都必须围绕“记录事项、查询事项、提醒执行”展开。

- 完成部署、运行说明、演示材料和发布版本准备。

## 13. 可演进方向：长任务拆分与任务重排

长任务拆分和任务重排可以作为时间管理产品的后续方向，但不是本周 MVP，也不作为当前 P0/P1/P2 的核心验收内容。这里只定义产品延伸原则，避免未来完全推倒重来。

### 13.1 长任务拆分

未来用户可以说：

> “我想在两周内完成产品需求报告，帮我拆成几个可执行事项。”

可能的延伸流程：

```text
长待办
  -> 询问截止时间、可投入时间和任务粒度
  -> 生成若干待确认的普通待办或日历事项
  -> 用户确认后批量创建
```

约束：

- 拆分结果必须先确认，不能直接生成正式事项。
- 初期只生成普通 Todo 或 CalendarEvent，不引入 Goal、Task 层级。
- 不自动占用已有时间，不静默移动日历。
- 拆分失败时保留原始长待办，不产生半成品。

### 13.2 任务重排

未来当用户说“今天没做完”或出现日历冲突时，系统可以生成调整候选：

```text
未完成事项或冲突
  -> 查询相关事项和可用时间
  -> 生成一个或少量调整候选
  -> 用户选择并确认
  -> 原子应用变更
```

约束：

- 只生成候选，不自动应用。
- 不能未经确认移动既有日历事项或改变截止时间。
- 重排应复用现有事项、提醒和确认机制，而不是新建一套独立业务闭环。
- 若没有可行方案，应展示原因，不制造看似完整的假计划。

### 13.3 当前 MVP 为未来方向保留的兼容性

本周不实现长任务拆分和重排，但基础事项模型和接口应满足：

- 日历和待办有稳定 ID、状态、时间和版本字段。
- 变更通过统一确认请求进入业务服务。
- 提醒与事项使用可追踪关联，未来批量调整时可以同步更新。
- 语音解析输出“操作 + 对象 + 参数”的结构，不把解析逻辑写死在某个页面或 Agent 中。

这些是扩展性约束，不代表本周要实现 Goal、Task、重排 Agent 或复杂规划能力。
